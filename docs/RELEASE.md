# BirdNest Release & Fleet Rollout Procedure

**Scope:** this document is the operational playbook for cutting a BirdNest
firmware release and rolling it out to a multi-camera fleet. It references
the design in [OTA_Design.md](OTA_Design.md) and the swarm review fixes
shipped in v0.1.3.

**Audience:** Miklós (release owner), and any future operator who takes
over the fleet management.

---

## 1. Pre-Release Checklist

Before tagging a release, verify each of the following. Items marked
**[must]** are release blockers; **[check]** are best-practice.

- [must] All 8 critical code patches from the v0.1.3 swarm review are on
  `main` (C-1 bootloader rollback, C-2 boot order, H-2 token failure,
  H-4 reset_config OTA NVS, M-9 local-build flag, M-10 battery fail-safe,
  M-11 otaHandle abort, M-2 SemVer parser). See §6 of the swarm review
  report for the consolidated list.
- [must] `pio run -e cam1_ota -e cam2_ota -e cam3_ota -e cam4_ota`
  builds clean on the Mac (the CI workflow covers this on `v*` tag push).
- [must] `sdkconfig.defaults` is in the repo root with
  `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y` (C-1).
- [must] `FW_VERSION` is auto-generated by the CI from the tag (no
  manual edit to `include/fw_version_auto.h`).
- [check] No uncommitted changes in the working tree.
- [check] `git status` clean on `main`; the working branch
  `release/v0.1.3-ota-code-fixes` has been merged via PR.
- [check] Release notes draft in [§3](#3-release-notes-template) below
  has been filled in and reviewed.

## 2. Tag & Release

**Sequence:**

1. Ensure `main` is fast-forwarded to the merge commit from the
   `release/v0.1.3-ota-code-fixes` PR.
2. Locally: `git tag -a v0.1.3 -m "OTA v0.1.3 — see release notes"`.
3. **Do not push the tag yourself** — the swarm review release gate
   requires Miklós's explicit approval before any tag push. Hand off
   to Alfred (the főségisztens) via Telegram / kanban comment.
4. CI workflow `.github/workflows/release-ota.yml` triggers on `v*`, runs
   `pio run -e release`, builds the `birdnest-esp32cam-v0.1.3.bin`
   asset, generates the SHA256 manifest, and attaches it to the GitHub
   release.
5. Verify the GitHub release page lists the asset and the manifest
   before proceeding to fleet rollout.

**Asset naming (v0.1.3):**

```
birdnest-esp32cam-v0.1.3.bin
birdnest-esp32cam-v0.1.3.bin.sha256
```

The `v`-prefix is preserved in the asset name; the build flag
`FW_VERSION` is set without the `v` (e.g. `0.1.3`).

## 3. Fleet Rollout Procedure

BirdNest targets a 4-camera fleet (`cam1`..`cam4`). A single bad release
would take all 4 cameras down at once, so rollout is staged.

**Stage 1 — pilot on `cam1` (day 1)**

1. Pick `cam1` as the pilot. Disable auto-update on the other 3 devices:
   from each camera's Telegram chat, send
   `/otaupdate_auto_off` and confirm with `/otastatus`.
2. On `cam1`, leave auto-update **off** for the first cycle. Run a
   manual check: `/otaupdate_check`. Confirm the response is
   `update_found` with `target_version=0.1.3`.
3. Run `/otaupdate_now` on `cam1`. Watch Telegram for the
   `health_confirmed` event (within 30 s of reboot) and the
   `health_confirmed_degraded` absence.
4. Inspect `cam1` for 24 hours: photos are capturing, MQTT telemetry
   arrives, deep sleep cycles are normal. Check `/otastatus` last_check
   and last_reason fields.

**Stage 2 — expand to `cam2`, `cam3`, `cam4` (day 2+)**

Only if Stage 1 was clean:

1. On each remaining camera, send `/otastatus` and confirm the running
   `current_version` is below `0.1.3`.
2. Send `/otaupdate_check` on each. Confirm the target is `0.1.3`.
3. Send `/otaupdate_now` on each, one at a time. Wait for the previous
   camera's `health_confirmed` event before moving on.
4. After all 4 are on `0.1.3`, run `/netdiag` on each to confirm WiFi
   RSSI, reconnect count, and MQTT round-trip.

**Stage 3 — re-enable auto-update (day 3+)**

Once the fleet is stable on `0.1.3` for at least 48 hours:

1. On each camera, send `/otaupdate_auto_on`.
2. Confirm with `/otastatus` that `auto: true` is now set.
3. Monitor the MQTT channel for `ota_update_start` and
   `ota_update_ok` events on the next auto-check cycle.

## 4. Rollback Plan

A bootloader-level rollback fires automatically if the new image fails
to mark itself valid within the IDF timeout (see C-1, §8.2.1 of the
design). For *runtime* issues (the new image boots but misbehaves), the
following manual rollback applies.

**Important:** the `/otarollback` command (swarm review C-3) is
**deferred to v0.1.4** — it is NOT in v0.1.3. Until then, the rollback
procedure is **LAN-side serial flash**.

### 4.1 Identifying a bad release

Symptoms of a runtime regression (not a brick):

- `health_confirmed_degraded` event in MQTT or Telegram debug.
- `/otastatus` `last_reason` is `health_probe_failed` or
  `health_confirmed_degraded`.
- Photos are blank, garbled, or absent.
- MQTT telemetry stops arriving while the device is still on WiFi.

### 4.2 Per-camera rollback (v0.1.3)

1. Move the laptop next to the affected camera; connect USB-TTL.
2. From the OTA-capable PlatformIO environment, run
   `pio run -e camN_ota -t upload` against the previous known-good
   release asset (e.g. `birdnest-esp32cam-v0.1.2.bin`).
3. After flash, monitor the serial port at 115200 baud; the device
   should print its `current_version` and `boot_count` in the first
   5 seconds.
4. Confirm via Telegram that `/otastatus` reports the expected
   `current_version` and no `pending_target`.

### 4.3 Fleet-wide rollback

If the bad release affects all 4 cameras and a fleet-wide revert is
needed, repeat §4.2 for each camera. If the camera is bricked (no
serial output, no WiFi), reflash over the ESP32-CAM USB-TTL header
following the manufacturer instructions.

## 5. Post-Release Monitoring

After Stage 3 of the rollout, monitor these signals for 7 days:

- **MQTT channel `birdnest/<label>/event`**: each camera should publish
  `boot`, `photo_taken`, `ota_update_ok` (or absent for the first 6
  weeks if there is no newer release). Any `ota_update_fail` or
  `ota_install_blocked` event is a yellow flag.
- **Telegram debug chat**: each camera sends a daily summary at level
  1; check that `/otastatus` last_check is recent.
- **Battery telemetry**: median battery voltage should not drop more
  than 0.1 V versus the pre-release baseline. A drop suggests a new
  wake-cycle regression.
